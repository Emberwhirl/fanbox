Frame measurement correction · 19 October 2026

The user confirmed sometimes minimizing or covering the test window. A controlled minimize/restore reproduced the same ~1,001 ms cadence while native BrowserWindow state recorded minimized/hidden/unfocused, with normal rendering restored afterwards and no long JavaScript tasks. Page visibility alone was misleading because the old harness disabled background throttling. Earlier one-second results do not establish a foreground application freeze: those runs did not record the required native window state.

The harness now samples native visible/minimized/focused state every 250 ms for both U6 and W. Losing the required foreground state produces an invalid measurement that fails the gate; raw frame data is retained, and the run cannot become a pass by ignoring bad intervals. Valid foreground runs retain the original 500 ms failure / 250 ms warning thresholds. Throttling is now neutral only where it must be: the Electron webContents preference is left at default (no application preference change survives in the product), while the two Chromium anti-throttling switches (--disable-renderer-backgrounding, --disable-background-timer-throttling) are still passed on harness launches (the harness launch args arrays in playwright-electron.js and frame-timing.cjs) — so the harness still stops Chromium from throttling background renderers, it just no longer flips the app's own throttling preference. A test-only notice reminds the user to keep the window foreground. The speculative application preference change was reverted; all 210 production files match the pre-investigation source.

Evidence under tests/artifacts/win-v2170-20261018/: frame-minimize-control.json and frame-window-guard.json demonstrate the negative control; frame-diagnosis.json contains the separate 80-second renderer/timer diagnostic. Dev-4 · A Chinese file name that matches a dictionary key is translated in English mode (SUPERSEDED — see below)

Found by review: the file list (.fname) is not excluded from translation. In English mode, a folder named exactly 输出 displays as "Output". The same was already true for existing keys such as 图片, 文档, 桌面 and 下载. It is display only; opening the folder still works.

Superseded (2026-10-19): this entry's original “Chosen: no change this round — the fix is to add .fname to the skip list in shared public/i18n.js” advice is void; do not follow it. The shipped fix is the Windows-only user-content marker approach described under “Changes implemented on Windows” above: Windows filename surfaces carry data-fanbox-user-content markers — only marker emission is win32-gated (isWindows()) — and the translator's skip of marked nodes is unconditional, inert wherever no markers exist, so POSIX behavior is unchanged. That approach is being completed in parallel — more filename surfaces are being marked — so this note describes the approach and deliberately pins no exact surface count. .fname (or any other filename selector) must never be added to the shared skip list in public/i18n.js: that would change English-mode behavior on macOS/Linux and break the Golden rule. Dropping the key is no fix either: the English panel would then show a Chinese row.

Dev-5 · Three review follow-ups go slightly beyond the plan's wording

Language fallback (D2). The plan's fallback was "the system language". In the bridge, which runs as Electron-as-Node, Intl reports the Windows regional format. The UI follows Chromium's display language instead, so a user with an English display language and a Chinese regional format, who never touched the toggle, would get 周 under an English UI. Windows PTYs now carry FANBOX_LANG = uiLang(). The bridge's order is config.lang (read live), then FANBOX_LANG, then Intl. POSIX PTY env is unchanged.

Git Bash lookup (6.4). Claude Code also accepts CLAUDE_CODE_GIT_BASH_PATH from the env block of its own settings.json. Without reading it, FanBox would silently leave out the quota line even though Claude Code would find bash. writeHookFiles now reads that file, read-only, when the process env lacks the variable.

curl (6.2). The plan's winFindExe('curl') expands PATHEXT, so a curl.cmd earlier on PATH would win, fail with EINVAL, and receive the token on stdin. The lookup is now the exact name winFindExe('curl.exe'), still PATH first and System32 second.
