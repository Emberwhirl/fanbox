Windows Port v2.12.1 — Remediation & macOS-Parity Plan

Fix plan for the 57 verified findings from the 2026-07-29 multi-agent review of master...dev. Goal: the Windows port behaves and reads exactly like the macOS original wherever the platform allows, and the macOS/Linux code paths return to byte-for-byte identical to master (the golden rule), so future upstream merges stay clean. Target release: v2.12.1 (package.json already reads 2.12.1 — no bump; the remediated port ships as the 2.12.1 Windows release). Target runtime: Windows 10/11 x64. All work lands on dev; windows is touched only to tag and release the tested port (§6).

Guiding principles

  • macOS is the reference UX. Every fix asks first: what does upstream v2.12.1 do on macOS? Windows mirrors that experience with platform-native vocabulary (Finder→资源管理器/File Explorer, 废纸篓→回收站/Recycle Bin, ⌘→Ctrl).
  • POSIX code returns to master text, not just master behavior. Where the port edited shared lines, we restore the master bytes and re-express the Windows behavior inside IS_WIN/PLATFORM === 'win32' branches — even when the edit was behavior-equivalent. This is what keeps the next upstream tag merge conflict-free.
  • Port rules stay load-bearing: argv-style spawns only, no shell strings containing user data, no parsing of where.exe/OEM-codepage output, taskkill /T /F for trees, busy tri-state where unknown = busy.
  • Target runtime: Windows 10/11 x64 only. ConPTY and PowerShell 5.1 are assumed present; no Windows 7/8.1 support, no ARM64/ia32 builds. Anything gated on older Windows is out of scope.
  • No macOS-only function or term may reach a Windows user. Every macOS-only surface — Finder, 废纸篓, ⌘, zsh, lsof, the pasteboard, dmg assets, IM6 convert, SIGKILL process groups — is eliminated from the Windows runtime and ported to its Windows x64 equivalent where one exists (mapping table below), degrading gracefully where none does. Elimination applies to the Windows experience only: in code, the macOS paths stay byte-for-byte per the golden rule.
  • Branch discipline: all port work happens on dev. windows exists solely to tag and release the tested port — dev is never merged into it until the port passes the full manual matrix on a physical Windows 10/11 x64 machine (§6).

Part I · 1 — High-severity fixes

HIGHH1+H3 · /fs/ mirror is dead for Windows drive-letter paths — HTML preview, preview assets, md local images all 404/403

server.js:2819 & :3081 · public/app.js:747 (fsUrl) — one root cause, both ends fixed together

fsUrl() packs C:\Users\me\page.html into a single URL segment; the server keeps the leading / when decoding, so the path normalizes to the invalid \C:\Users\… and every /fs/ feature fails (closed) on Windows.

Decision D1 — URL shape for Windows paths (recommended: Option A).
Option A (chosen): keep /fs/ URLs POSIX-shaped, mirroring the file:///C:/… convention: fsUrl() splits on both separators (/[\\/]/) only when state.sep === '\\' — POSIX keeps master's p.split('/'), so a macOS filename legally containing a backslash still resolves — → /fs/C:/Users/me/page.html; server-side (both servers), after decoding, a win32-only step strips the leading slash when /^\/[A-Za-z]:[\\/]/ matches. Because each path component stays its own URL segment, relative asset references inside previewed HTML keep resolving — identical to macOS preview behavior. The injected file://→/fs rewrite maps file:///C:/x → /fs/C:/x for free.
Option B (rejected): encode the whole path as one opaque segment and decode server-side — breaks relative-asset resolution in the preview iframe, deviating from macOS UX.

Companion hardening (win32 branch only): previewPathAllowed's $HOME-subtree containment compare becomes case-insensitive and separator-normalized on Windows (NTFS is case-insensitive; the current check is trivially bypassed by casing — it must fail closed correctly, not accidentally). POSIX compare untouched.

UX result: preview iframe, relative assets, markdown local images, file-follow — all behave exactly as on macOS.

HIGHH2 · WeChat timeout kill orphans the real agent — tokens keep burning

electron/wechat/driver.js:118–119

kill() fires taskkill /T /F async and then immediately child.kill()s the root. The root dies first, taskkill finds no tree, and the grandchild (node.exe → codex.js → codex.exe) survives — up to 3 orphans with the retry loop.

Fix (no alternatives worth weighing): invert the order — run taskkill to completion first; call child.kill() only in taskkill's callback (as fallback for taskkill failure/ENOENT). Keep the 5 s taskkill timeout; log (don't swallow) a non-zero taskkill exit. Audit confirms this is the only tree-kill site in the port.

UX result: matches macOS SIGKILL-the-group semantics: after a timeout, nothing of the agent survives, and the WeChat retry loop starts from a clean slate.

HIGHH4 · Right-click menu shows Chinese in EN mode on every platform (macOS regression)

public/app.js:1968 · i18n-dict.js:171

The port replaced master's literal 「在 Finder 显示」 with `在 ${fileManagerName()} 显示` → 「在 访达 显示」 on macOS — a string with no dict key, so EN users see Chinese; on macOS this is a visible regression from upstream.

Decision D2 — restore master on macOS, platform-name elsewhere (recommended). macOS renders master's exact 「在 Finder 显示」 (existing dict key works again). fileManagerName() survives only inside the non-darwin arms: Windows 「在 资源管理器 显示」 → “Reveal in File Explorer”, Linux/browser 「在 文件管理器 显示」 → “Reveal in File Manager” (new dict keys, §3). Alternative — keep 访达 as the macOS label and add a dict key: rejected; it deviates from master's UI text for zero benefit.

Part I · 2 — Platform-policy & architecture decisions

Each of these changes what a Windows user experiences, or how the fork relates to upstream. Defaults below are what I'll implement unless you override.

D3 · Git / MSYS tools currently speak Chinese to every Windows user

electron/main.js:769 MED

The mac-motivated fallback forces LANG=zh_CN.UTF-8 into every Windows PTY (LANG is never pre-set on Windows), so Git for Windows localizes its output to Chinese regardless of the user's locale — and pattern-matching agents see localized git text.

Recommended: don't set LANG at all on win32 (restore the POSIX line to master bytes; the whole fallback becomes non-win32). Git and MSYS tools then follow the OS display language — native Windows behavior, and consistent for agents. Alternatives: (b) LANG=C.UTF-8 — forces English even for zh-CN users, worse; (c) derive from FanBox's own language setting — couples terminal env to app UI language, surprising.

D4 · Scheduled-task (cron) tabs: always spawn PowerShell on Windows

server.js:2668 (cronShq) LOW

cronShq quotes the agent prompt for PowerShell, but the PTY shell is user-configurable to cmd.exe, where single quotes are literal and &/%VAR% get interpreted — a scheduled prompt like 「backup logs & prune old ones」 silently splits.

Recommended: agent-type cron tabs (claude/codex prompts, the ones cronShq quotes) always launch PowerShell on Windows, regardless of the user's default shell. One quoting discipline, semantics match macOS-cron-spawns-zsh. Shell-type tasks (t.agent === 'shell', raw command typed verbatim) are exempt — they run in the user's default shell exactly as authored.
Plumbing note: agentCreate has no shell parameter today — this adds an opts.shell threaded through the whole channel: global.__fanboxAgent.create → agent:term-create IPC payload → renderer tab-create handler → fanboxPty.spawn → pty:spawn handler → shell override. Pure win32-gated addition; POSIX signatures and behavior stay master. Alternative — cmd-aware quoting: rejected; building cmd-safe strings is exactly what the port rules call unfixable.

D5 · WeChat bridge: remove the PowerShell string-building fallback

electron/wechat/driver.js:96–102 MED

When resolveWinCli() can't parse an npm shim, the bridge falls back to powershell -Command "…persona text…" — user-authored config embedded in a shell string (rule 1 violation; the “unreachable” comment was disproven with a hand-written claude.cmd).

Recommended: delete the fallback. Extend resolveWinCli to first check for a real claude.exe/codex.exe on PATH (standalone installs — spawn directly, argv-style), then npm-shim resolution as today. If both fail, reply over WeChat with the same “CLI not found — install it with npm i -g …” message the desktop flow shows. Predictable failure beats a quoting-hazard code path. Alternative — keep fallback but via -EncodedCommand + args array: still executes through a shell for no gain once the exe probe exists.

D6 · Thumbnails: never run bare convert on Windows

server.js:1625, :1788 MED

Bare convert on Windows resolves to System32's FAT→NTFS utility (System32 precedes user PATH), so the ImageMagick-6 fallback can never work — and FanBox executes an unrelated disk tool with user paths as arguments.

Recommended: win32 thumbnail/HEIC chain = magick (IM7, resolved via winFindExe) → ffmpeg → give up (frontend already renders a generic tile). IM6-on-Windows is not worth supporting. The POSIX chain returns to master bytes (see D8 for the Linux consequence).

D7 · Copy/paste files: complete the round-trip on Windows

electron/main.js:827 (clip:read) LOW · :857 (clip:file) MED

Today the port writes files to the clipboard (with a wildcard bug) but never reads Explorer-copied files — so “copy in Explorer → paste path into terminal”, which works on macOS, silently yields nothing.

Recommended: implement the read side via clipboard.readBuffer('FileNameW') in a win32 branch of clip:read, returning the same {kind:'file'} shape as the darwin pasteboard path — Explorer-copied files paste their quoted path into the terminal exactly like Finder-copied files do. Two implementation caveats: the buffer is NUL-terminated UTF-16LE (strip the trailing \0 or the path is corrupt), and FileNameW carries only the first file of a multi-select copy — acceptable, since the macOS public.file-url path is single-file too. The write side switches to Set-Clipboard -LiteralPath with the path delivered via environment variable (fixes both the wildcard bug for report[1].png-style names and the rule-1 violation); it must keep spawning powershell.exe 5.1 — pwsh 6+ removed Set-Clipboard's file support.

D8 · Linux stance: strict restore, no Linux-only improvements in this fork

main.js:75, :127 · server.js:1616 · app.js:5533 LOW ×4

Several port edits improve or alter Linux behavior (window chrome, quit label, thumbnail pipeline, ⌘→Ctrl chrome rewriting, sleep-blocker calls). They all violate byte-for-byte and none serve the fork's mission — this repo ships Windows; upstream ships macOS; nobody ships Linux.

Recommended: restore every one to master bytes; keep improvements only where they can live inside IS_WIN. Linux keeps behaving exactly like upstream (warts included). Alternative — keep Linux niceties behind isLinux() branches: defensible, but it grows a third platform surface nobody tests. Say the word if you want this instead.

D9 · FANBOX_SHELL must beat an inherited SHELL

electron/main.js:735 LOW

Recommended: reorder the win32 candidate list to FANBOX_SHELL → SHELL → powershell.exe. The port-specific explicit setting should never lose to an env var leaked in by MSYS/Git-Bash. (POSIX list untouched — it doesn't have FANBOX_SHELL.)

D10 · macOS behavioral parity restorations (the four that change what users/agents observe)

main.js:916 · :796 · :930 · :60 MED ×4

These four shared-path edits changed macOS runtime behavior and each gets platform-forked (POSIX = master bytes, Windows keeps the port behavior):

  • Busy detection — BARE_SHELL_RE gained powershell|pwsh|cmd; on macOS a user sitting inside pwsh now reads idle, so a sibling agent will type into their running program. Split into POSIX regex (master) + win32 regex.
  • OSC stripping in the PTY data path — changes /api/agent/read output and WeChat tails on macOS (breaks until regexes written against upstream). OSC strip becomes win32-only.
  • cwd fallback — macOS pty:cwd/agentList now report a stale spawn-time dir when lsof fails, instead of upstream's honest {ok:false} (mis-navigates the file pane; feeds stale cwd to agents). Fallback becomes win32-only (it IS the Windows mechanism; Windows has no lsof).
  • Window startup — show:false + ready-to-show now hides the macOS window during boot (and forever, if the renderer fails). Gate to win32, where it was presumably added against white-flash.

Part II · 6 — Phasing, verification, release

Phases (each lands as its own conventional commit on dev)

  1. P1 highs: D1 /fs scheme (both ends + preview containment), taskkill ordering, Finder-label revert.
  2. P2 user-facing: §3 dict entries + copy reverts, D3 LANG, D6 thumbnails, D7 clipboard both ways, badge.
  3. P3 golden-rule sweep: the §4 table, file by file (main.js → server.js → wechat → app.js).
  4. P4 mechanical: remaining §5 rows (snapEligible casing, trashPath argv, winDirSizes, disk panel, md fallback, which-cache, cron shell, FANBOX_SHELL, PATH quotes).

Acceptance

  • Golden-rule audit (the load-bearing check): after P3, review git diff master...dev for the five core JS files and require every remaining hunk to fall into one of three accepted categories: (a) inside an IS_WIN/isWindows()/PLATFORM==='win32' guard; (b) a pure addition (new win-only function, new dict entries); (c) a whitelisted one-liner rewrite whose only behavioral branch is behind a platform/sep guard — unavoidable for shared one-line sites like dirOf, fsUrl, i18n-dict.js:24, and the REL_* constant selections, where the guard necessarily lives inside the hunk. Preserve the reviewed diff as experiments/winport-parity-202607/ with a verify.js that mechanically re-checks “no hunk outside categories a/b/c” (category c against the explicit whitelist) — per the repo's acceptance-campaign convention.
  • Per-commit: node --check on every touched file; server smoke test (FANBOX_NO_OPEN=1 FANBOX_PORT=45991 node server.js + the three curl probes).
  • macOS-term leak audit: grep the Windows-reachable surface (win32 branches, shared frontend strings, EN dict values selected on Windows) for Finder/访达/废纸篓/⌘/dmg/zsh/lsof/pbpaste/osascript — nothing macOS-only may be visible or executable on Windows (occurrences inside darwin-only arms are fine); cross-check against the §“macOS-only surface” mapping table.
  • Windows manual matrix — run on a physical Windows 10/11 x64 machine; passing it is the merge gate for dev → windows: HTML preview with relative assets; md with relative + absolute local images; EN-mode trash flow (menu → confirm → toast); Explorer copy → paste into terminal; report[1].png copy-file; WeChat codex timeout → tasklist shows no orphan; ffmpeg under a CJK username; IM7 thumbnails; snapshot attempt from a c:\users\…-cased cwd (must refuse); scheduled task with & in the prompt; disk-panel descend/ascend; update check against a docs-only release (no toast).
  • macOS regression: textual — the §4 audit above is the macOS test (byte-identical code needs no behavioral retest); plus one smoke build if convenient.

Release — target v2.12.1, gated on real-Windows testing

  • Version stays 2.12.1. package.json already reads 2.12.1 and the CHANGELOG already carries a [2.12.1] → ### Windows port subsection; remediation entries (root-cause narratives) are folded into that subsection as each phase lands. No 2.12.2, no version bump — the remediated port is the v2.12.1 Windows release.
  • All remediation commits land on dev. windows is the release line only: do not merge dev → windows until the full Windows manual matrix above passes on a physical Windows 10/11 x64 machine.
  • Once the matrix passes: merge dev → windows, tag, and publish the GitHub Release with both assets attached at publish time (FanBox-2.12.1-win-x64.exe + -portable.exe).
